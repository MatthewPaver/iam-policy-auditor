# Walkthrough evidence and limits

[Open the walkthrough](https://matthewpaver.github.io/iam-policy-auditor/impact/) · [Review your own policies](https://matthewpaver.github.io/iam-policy-auditor/?view=review) · [Automated checks](https://github.com/MatthewPaver/iam-policy-auditor/actions)

The example asks whether a report reader can still open a report after permission to delete a database is removed. Three choices keep both permissions, block everything, or retain only report access. The same local PolicyLens engine evaluates every choice. Animation illustrates the returned decisions; it does not make them.

## Inspect or reproduce

The walkthrough exposes source rules and exact statement changes beside the result. Export the review JSON to retain supplied policies, declared requests, decisions, source citations, input identities and limits. SHA-256 identities identify the supplied bytes; they do not certify correctness or protect a downloaded record from editing.

## Limits

The report, database and actions are fictional. No AWS account connects and no cloud action occurs. The authored sandbox effects are not an operations forecast, construction simulation or digital twin. The report is independent of the example database.

Verification covers only the declared requests and supplied context. It does not establish account-wide safety or production approval. Unsupported semantics stay unresolved. The 86 reference/regression cases derive from documentation; no live AWS comparison or real-user comprehension study is claimed. Synthetic MiroFish feedback, when available, is exploratory feedback rather than user research or security validation.

Historical before-and-after captures remain in the portfolio case study: [PolicyLens design journey](https://matthewpaver.github.io/work/policylens/). Current journey captures are generated by `npm run test:simulation` under `test-results/simulation`; historical captures are not overwritten by the product build.
